# 智能日报生成器：代码讲解与答辩准备

## 先用 30 秒介绍项目

这是一个基于《SDD 实战》分层思路实现的智能日报生成器。命令行入口 `main.py` 和 Web 页面共用 GitHub、飞书采集器及日报生成器。Web 端由 Python HTTP 服务提供 API，前端通过 API 生成、查询和展示日报；日报保存在 SQLite，可复制、下载 Markdown，也可在真实模式下发送邮件。Mock 模式用于离线演示和自动化测试，避免测试时访问真实平台或误发邮件。

主要链路：

```text
GitHub 提交 / 飞书任务 API
       ↓
collector/ 采集结构化活动
       ↓
generator/ 汇总并生成 Markdown、HTML
       ↓
SQLite 保存 ← web_backend/service.py 协调业务
       ↓
web_server.py 提供 HTTP API ← web_ui/ 页面调用
       ↓
邮件 / 飞书机器人
```

## 按目录看代码

| 文件/目录 | 作用 | 老师可能追问 |
|---|---|---|
| `main.py` | 命令行主流程：读取配置、采集数据、生成日报并按参数决定是否推送；也供 GitHub 定时工作流运行。 | 为什么还有 CLI？因为定时任务和 Web 页面是不同入口，但可以复用业务模块。 |
| `collector/github.py` | 调 GitHub API 获取提交及变更统计，处理分页、时间范围、错误和重试。 | 数据按什么时间筛？API 返回的提交时间与日报时间窗口。 |
| `collector/lark_task.py` | 获取飞书项目/任务状态变更，整理为统一任务记录。 | 为什么可能是 0 条？项目 ID、权限、时间范围或当天没有符合条件的任务。 |
| `generator/formatter.py` | 定义提交、任务、成员日报等数据模型，并聚合成 `DailyReport`。 | 采集和排版为什么分开？方便独立测试、替换数据源或模板。 |
| `generator/template.py` | 将日报模型渲染为 Markdown 和 HTML。 | 两种格式分别用于什么？Markdown 便于复制/下载，HTML 用于网页和邮件展示。 |
| `web_server.py` | Python HTTP 服务入口：静态页面、API 路由、JSON 响应、健康检查、生产环境 Basic Auth。 | 为什么用 `0.0.0.0:$PORT`？托管平台需要服务监听公网接口和平台分配的端口。 |
| `web_backend/service.py` | Web 业务层：生成/查询日报、统计图表数据、发邮件、处理重复发送保护。 | HTTP 层与业务层分开有什么好处？接口代码不直接混入采集和生成逻辑，便于测试。 |
| `web_backend/real_adapter.py` | 将真实 GitHub/飞书采集器接入 Web 服务，并按活动发生日期计算今天和近七日数据。 | 为什么图表看实时活动而非日报历史？避免某天没生成日报就漏掉那天的活动。 |
| `web_backend/mock_adapter.py` | 提供固定演示数据，不访问外部平台。 | 如何防止 Mock 数据被当成真实数据？界面显示模式；Mock 模式拒绝真实邮件发送。 |
| `web_ui/index.html` | 页面结构和组件容器。 | 前端如何与后端交互？由 `app.js` 请求 `/api/...`，不是直接读数据库。 |
| `web_ui/app.js` | 加载任务/日报/分析数据，生成日报、筛选搜索、打开详情、复制和导出。 | 加载失败怎么办？显示错误并提供重试，保留已有列表，不把失败伪装成 0 条。 |
| `web_ui/style.css` | 页面布局、图表卡片、响应式和窄屏样式。 | 怎么验证手机布局？Playwright 在桌面和 390px 窄屏视口检查溢出。 |
| `notifier/email.py` | 通过 SMTP 发送 HTML 日报邮件，并嵌入图表资源。 | 如何避免重复发？成功后将发送时间写入 SQLite；重新生成后按生成时间判断旧发送记录是否仍有效。 |
| `notifier/charts.py` | 根据活动统计生成邮件可显示的图表内容。 | 邮件图和网页图为什么可能不同？网页由前端绘制；邮件采用适合邮件客户端的嵌入式图表。 |
| `notifier/lark_bot.py` | 将日报推送到飞书机器人。 | 读取群聊吗？不读取群消息；这里只向配置的飞书接收目标推送日报。 |
| `shared/config.py` | 读取并校验配置，构造类型化配置对象；支持从环境变量读取云端配置。 | 密钥放哪？本地 `.env`/`config.yaml`，托管环境放 Secrets，不进 Git。 |
| `shared/env.py` | 加载本地 `.env` 环境变量。 | 为什么不直接把密钥写代码？防止泄漏并支持不同环境配置。 |
| `shared/storage.py` | SQLite 表结构、日报保存/查询、同日更新与邮件发送记录。 | 为什么同一天再生成不重复新增？日期和团队有唯一约束，重生成更新当日报告。 |
| `shared/logger.py` / `errors.py` | 统一 JSON 日志和分层异常类型。 | 日志有什么用？线上定位数据源、邮件或 API 失败，同时不把内部堆栈直接暴露给页面。 |
| `config.yaml.example` | 不含真实凭据的配置样例。 | 为什么不上传 `config.yaml`？本地文件包含账号/密钥等敏感信息。 |
| `pyproject.toml` / `uv.lock` | Python 项目元数据、依赖声明及锁定版本。 | CI 和本地环境如何尽量一致？使用明确依赖，并在 CI 安装后运行相同测试。 |
| `.github/workflows/ci.yml` | push/PR 时跑 Python 3.11、3.12 测试、Render 配置校验和浏览器测试；定时/手动任务在测试成功后发邮件。 | push 为什么不发邮件？为避免每次提交都触发真实邮件；只有 schedule 或 main 上手动触发才发。 |
| `render.yaml` | Render Blueprint 部署定义：Python 服务、启动命令、健康检查、持久磁盘、环境变量占位和检查通过后自动部署。 | 这是否证明网站已上线？不是；需在 Render 真正创建/连接服务并看到部署 Live。 |
| `tests/` | 单元、接口、集成及浏览器端到端测试。 | Mock 测试证明了什么？证明内部逻辑和接口链路，不等于外部 GitHub/飞书服务永不故障。 |
| `specs/` | SDD 需求提案、设计和任务拆解。 | 规范驱动开发怎么体现？先明确需求/验收，再设计和分任务，最后按验收测试实现。 |
| `docs/superpowers/` | 本轮批准的设计、计划、执行进度和验证记录。 | 插件是否安装？记录说明当时 Superpowers 插件未安装；本轮按其公开技能文档执行流程，不声称插件已安装或被调用。 |

## 关键 API（老师可以现场点页面验证）

- `GET /api/health`：查看服务状态、真实/Mock 模式，不返回凭据。
- `GET /api/analytics`：今日活动分布及近七个自然日强度。
- `GET /api/reports`：日报历史列表。
- `POST /api/reports`：生成并保存当日日报。
- `GET /api/reports/<id>`：读取日报详情。
- `POST /api/reports/<id>/email`：发送对应日报；Mock 模式拒绝发送，已成功发送的日报会防重复。
- `GET /healthz`：部署平台健康检查，不代表业务 API 的每项功能都已验证。

## 老师最可能问的 8 个问题

1. **你负责的核心流程是什么？** 说明“采集 → 统一模型 → 生成 Markdown/HTML → SQLite → 页面/邮件”，指出每层对应的文件。
2. **怎么区分真实数据和 Mock？** 真实模式由配置和凭据启用真实适配器；Mock 适合离线测试，页面有模式提示且不能真实发邮件。
3. **API 失败时会不会显示 0 活动？** 不应该。采集状态单独返回并提示失败，避免把“没有数据”和“数据没采到”混为一谈。
4. **为什么昨天的提交会出现在近七日图表？** 统计直接按真实活动时间窗口采集，不依赖昨天是否已经生成一份日报。
5. **如何防重复日报和邮件？** SQLite 对日期/团队设唯一约束，同日重生成更新记录；邮件成功后保存发送时间并在发送入口再次检查。
6. **如何保证前端内容安全？** API 返回 JSON；日报正文按文本展示，不把外部消息作为任意 HTML 执行；生产页面/API 有 Basic Auth。
7. **测了什么、没测什么？** Python 单元/API 测试、Mock HTTP 链路、Playwright 浏览器交互；真实凭据下的 GitHub/飞书全量行为、Render 线上部署需要单独说明，不能由 Mock 测试替代。
8. **CI/CD 到什么程度？** GitHub Actions 的 Python 3.11/3.12 测试通过；定时邮件在 schedule 或 main 手动触发且测试通过后执行。`render.yaml` 已配置 CD，但只有 Render 服务实际创建并显示 Live 才能称线上部署完成。

## 现场讲解顺序

1. 先打开 `README.md` 和 `specs/design.md` 说明需求与分层。
2. 从 `main.py` 讲原有 CLI，再讲 `web_server.py` 如何提供页面 API。
3. 跟着 `web_backend/service.py` 讲生成、SQLite、邮件和分析数据。
4. 打开 `collector/`、`generator/`、`notifier/` 各选一个关键文件说明职责。
5. 最后看 `tests/`、`.github/workflows/ci.yml`、`render.yaml` 说明如何验证和部署。

## 现场注意

- 不要把 `.env`、真实 `config.yaml`、访问令牌、SMTP 密码投屏或提交到仓库；演示配置结构用 `config.yaml.example`。
- 明确说清楚已验证的范围：当前 GitHub Actions 截图显示 Python 3.11/3.12 检查成功；邮件任务也曾成功发送。Render 的线上站点仍需以 Render 控制台的部署状态为准。
- 如果老师问“哪里是 AI”，如实回答：当前重点是自动采集、规则筛选、结构化汇总和模板生成；没有接入大模型时，不要把规则模板说成 AI 自动理解或总结。
